### G01-01 comparison

15 November 2026. Source comparison only. No charts, workspace modes, or endpoints were added. The inventory row stays **Gap**.

Admin `/admin` widgets, in order: `CompanySetupReminder`, `FieldWorkspace`, `FieldActivityStatsWidget`, then the signed-in user's chart selection. Header actions are punch, a session period, Customize, and All charts.

Fields and actions that already exist:

- Setup reminder shows when `Onboarding::canAccess()` is true, the session has not deferred it, `users.company_setup_reminder_dismissed_at` is null, and company setup is incomplete. `Onboarding::canAccess()` requires the current tenant and `super_admin` or `administration_admin`. Remind later stores a session flag. Dismiss writes the timestamp. Both abort unless onboarding access is allowed.
- Personal workspace cards: Start visit when `supports_direct_calls` and `VisitResource::canCreate()`; otherwise Open monthly plans when `SalesTourPlanResource::canViewAny()`. Plan visits when `supports_flexible_plans` and `FlexiblePlanning::canAccess()`. My DCRs when `SalesDcrResource::canViewAny()`. Coverage when `FieldCoverage::canAccess()` and `FieldTeamOnboardingService::canManage()` is false.
- Team cards, shown with the switch only when both sides have cards: Company launch from `CompanyLaunchService::readiness()` when onboarding access is allowed; My approvals when `MyApprovals::canAccess()` and the user can manage a team or has a pending assigned step; Team coverage when the user can manage a team and coverage access is allowed.
- Today counts from `DashboardMetrics`: visits today excluding cancelled (`applyVisibility('Visit')`); pending DCRs in `draft` or `pending` (`applyVisibility('SalesDcr')`); current pending approval steps assigned to the user; punched-in attendance for today. The punch count is unscoped for `super_admin`, `administration_admin`, or `AccessAllRecords`, and otherwise limited to `PositionService::getVisibleUserIdsFor()` through `employees.login_id`. Links go to Today's Visits, DCR Register, My Approvals, and Attendance Register.
- Periods are `today`, `last_7` (default), `this_month`, and `last_30`, stored in the dashboard session. Charts are Calls by day, Call status, DCR status, Plan and calls, Field expenses, Calls by person, and Average calls. `users.dashboard_widgets` stores the sanitized selection; null means all seven. Chart visibility is that selection. Series use `FieldVisualReport` with the matching `applyVisibility` scope. Customize and All charts write only that user column.
- Punch actions appear only when the user has a linked employee. Punch In requires latitude, longitude, and `currentShiftForDate(today())`, then writes `DailyAttendance` on `employees.id` and an in punch sourced `punch-in-page`. Punch Out requires coordinates and today's attendance, writes an out punch sourced `dashboard`, and runs `ProcessDailyAttendanceJob`. A completed day is disabled.

`GET /api/v1/me` returns `id`, `name`, `email`, `date_format`, `field_planning`, `optional_modules`, `company_launch` from `forUser()`, and the linked employee `id`, `employee_id`, `first_name`, `last_name`, and `mobile_number`. It does not return dashboard widget keys or chart series. `GET /api/v1/dashboard/today` returns the four Today counts from `DashboardMetrics` for the signed-in user. `company_launch` is the signed-in user's launch snapshot. The team card uses `readiness()`.

Today's Tour already punches through the attendance API when the `hr` module is allowed, opens today's DCR, and searches Doctors, Monthly Tour Plan when `supports_mtp`, Plan visits when `supports_flexible_plans`, Attendance & leave when `hr` is allowed, and Sales Assistant. Direct-call Doctors open the account list; other modes pass the loaded tour territory and patches. Today's Tour also shows the four counts from `GET /api/v1/dashboard/today` when that read succeeds. Coverage, approvals, onboarding, chart selection, and the setup reminder remain on the Admin dashboard.

### G01-02 comparison

15 November 2026. Source comparison only. Punch writes were not changed. The inventory row stays **Unassessed**.

Admin Punch In/Out is `/admin/punch-in`. `shouldRegisterNavigation()` is true only for the `marketing` role. The page has no `canAccess()` override. `RedirectMarketingToPunchIn` sends a `marketing` user to that page until a `DailyAttendance` row exists for today on the linked `employees.id`. The same punch actions are on the Dashboard for any signed-in user with a linked employee.

Both web actions require latitude and longitude. With no row today the button is Punch In. With a row and no `out` punch it is Punch Out. Otherwise it is the disabled label Attendance Completed. Punch In also requires `currentShiftForDate(today())` and writes `DailyAttendance.employee_id` as `employees.id`, status code `SP` when that status exists, and an `in` punch sourced `punch-in-page`. The payload stores IP, latitude, and longitude. Punch Out writes an `out` punch sourced `dashboard` and runs `ProcessDailyAttendanceJob` with `dispatch_sync`. The web methods do not send `recorded_at` or `device_id`, and they do not reject a repeated in or out inside the action.

`PunchRequest` allows any authenticated API user. The body is `latitude` and `longitude`, optional `recorded_at`, `source`, and `device_id`. `recorded_at` must be within the last seven days and no more than five minutes ahead; when omitted, the API uses the current time. `GET /attendance/today` and `GET /attendance?month=Y-m` return the linked employee's rows, or null/empty when no employee is linked. Punch In returns 422 for a missing employee, missing coordinates, an existing row that day, or no active shift. It stores source `field-api` unless a source is sent, plus `device_id`, `user_id`, `recorded_at`, and `received_at`. Punch Out returns 422 when today's row is missing, an `out` punch already exists, or the time is before `first_punch_in`. It then runs the attendance job in the request. Both writes use `employees.id`.

`tests/Feature/Api/V1/AttendanceApiTest.php` covers a missing employee, a missing shift, a second punch-in, and a punch-out before punch-in. Today's Tour shows Punch in, Punch out, or disabled Done when the `hr` module is allowed, including when module flags are absent. The profile sheet uses the same card. The control calls `POST /attendance/punch-in` or `POST /attendance/punch-out` with the current latitude and longitude, source `flutter`, and a device id. It does not send `recorded_at`. Success starts or stops the GPS trail. A failure stays on the tour and shows the API or location message. The mobile menu item `g01-02` follows the marketing navigation check and opens Today's Tour. There is no queued punch path.

### G01-04 comparison

15 November 2026. Source comparison only. No approvals inbox was added. The inventory row stays **Gap**.

Admin My Approvals has no `canAccess()` override. The table lists `ApprovalStep` rows assigned to the signed-in `users.id`, with status pending, whose `step_order` is the lowest pending step on that approval. Columns are the approvable class name, the approvable id, the requester name, and the request time. Approve asks for confirmation and calls `ApprovalService::approve` without comments. Reject requires comments and calls `ApprovalService::reject`. The service locks the approval and returns false when it is finalized, no longer pending, or the current pending step belongs to someone else. A matching approve records the step, and finalizes the approval when every step is approved. A matching reject records the comments and finalizes the approval as rejected. The empty state says there is nothing waiting.

`GET /api/v1/dashboard/today` counts those same current assigned steps as `pending_approvals`. There is no generic inbox or decision route. Monthly tour plans are the mobile decision path: `GET /monthly-tour-plans/inbox` lists other users' plans for a month when MTP is on and that module requires approval, limited to the current pending step assigned to the caller. `POST /monthly-tour-plans/{plan}/approve` and `reject` require the plan revision. Reject also requires comments. `FieldMtpService::canDecide` is false for the plan owner, a finalized approval, and any user who is not the current assignee. The Flutter MTP screen shows that inbox and the approve/reject actions. DCR, leave, SGIP, and account screens show their own approval status and do not decide a generic step. My Approvals is not one of the schema 1 navigation screens. `tests/Feature/ApprovalFrameworkTest.php` covers a non-assignee approve: the call returns false, the approval stays pending, the current step stays pending and assigned to the original user, and no approved activity is written.
